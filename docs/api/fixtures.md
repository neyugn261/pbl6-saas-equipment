# Development fixtures (fixed ids)

Dev seeds of different services refer to each other only by these ids, so
each service can seed its own database independently and the data still fits
together. Add a row here in the same PR that adds the seed.

| Entity | Id | Code / name | Seeded by | Used by |
|---|---|---|---|---|
| Tenant DEMO | `00000000-0000-4000-8000-000000000001` | `DEMO` | identity (`tenant_directory`); organization (`tenants`) | every service |
| Customer DEMO-CUST-01 | `00000000-0000-4000-8000-000000000101` | `DEMO-CUST-01` Bệnh viện Đa khoa Demo | organization | identity (`user_customer_links`), asset, service-request |
| Customer DEMO-CUST-02 | `00000000-0000-4000-8000-000000000102` | `DEMO-CUST-02` Nhà máy Cơ khí Demo (no demo account: customer isolation) | organization | asset, service-request |
| Membership of `customer.admin@demo.local` | `00000000-0000-4000-8000-000000000201` | → DEMO-CUST-01 | organization; identity link also seeded | identity |
| Membership of `customer.user@demo.local` | `00000000-0000-4000-8000-000000000202` | → DEMO-CUST-01 | organization; identity link also seeded | identity |

| Branch DN | `00000000-0000-4000-8000-000000000302` | `DN` | organization | — |

User ids are generated by Identity's seed; services that need them look them
up by email at seed time (or read them from a token in tests). Organization's
seed logs the demo accounts in through Identity's API (`SEED_DEMO_PASSWORD`)
and reads `user.id`; it never reads identity_db.

Demo accounts and password: root [README](../../README.md#5-chạy-identity-service).

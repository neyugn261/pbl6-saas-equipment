# Development fixtures — two-branch demo

Source of truth: [`scripts/demo/catalog.cjs`](../../scripts/demo/catalog.cjs). Root commands: `pnpm demo:seed` (preserve progress), `pnpm demo:reset` (replace local application data), `pnpm test:demo-seed` (dedicated test databases). Full account table and scenarios: [demo guide](../user-guide/demo-data.md).

`…NNNN` below abbreviates `00000000-0000-4000-8000-00000000NNNN`. Cross-service IDs are logical references; each service seeds only its own DB. User IDs are generated by Identity and resolved by authenticated API, never cross-database SQL.

| Entity | Fixed IDs | Meaning / owner |
| --- | --- | --- |
| Tenant | `…0001` | DEMO; Organization owns it, Identity holds its directory projection |
| Branches | `…0301`, `…0302` | HCM, DN |
| Customers | `…0101`, `…0102` | Hospital, Factory; shared within tenant |
| Customer memberships | `…0201`–`…0204` | Hospital Admin/User; Factory Admin/User |
| Customer sites | `…0401`–`…0404` | Hospital HCM, Hospital DN, Factory DN, Factory HCM |
| Locations | `…0501`–`…0508` | Technical area and operation room at each site, parent before child |
| Contacts | `…0601`–`…0604` | Two contacts per customer |
| Equipment models | `…1001`, `…1002` | US-100, PUMP-200 |
| Equipment | `…1101`–`…1106` | Codes SA-001…003 and MB-001…003; three served by each branch |
| Warranties | `…1201`, `…1202`, `…1204`–`…1206` | 01/04/05/06 current; 02 expired; 03 has no warranty row |
| Registration history | `…1301`–`…1306` | Asset REGISTERED entries |
| Maintenance plans | `…3001`, `…3002` | Equipment 05 HCM and 03 DN; quarterly, initially due on seed day |
| Technician profiles | `…4001`–`…4004` | HCM 01/02, DN 01/02; Identity user IDs resolved through API |
| Skills | `…4101`–`…4103` | Diagnosis, maintenance, repair |
| Parts | `…5001`–`…5003` | LOC-01, CC-5A, CB-AS01 |
| Warehouses | `…5101`, `…5102` | K-HCM, K-DN |
| Initial receipt keys | `…5201`–`…5206` | Stable key per warehouse/part; zero initial quantity has no artificial RECEIVE |
| Policy/checklist item IDs | `…6001`–`…6203` | Stable IDs inside two published maintenance profile bodies |

Policies, QR, requests, estimates, WO, reports, attachments, registrations and tasks use IDs generated by owning APIs/scheduler. Stable codes, scenario titles, idempotency keys and a local resumable seed journal prevent duplicates. No fake Task/WO/history/notification is inserted.

Request titles describe the reported fault without scenario/status prefixes. `DEMO-*` scenario keys are private journal/idempotency identifiers only; no longer stored as a business title. Three WO originate from these requests; two more originate from maintenance tasks.

Dates are relative to the first seed day and preserved on rerun. Existing metadata, stock, routing, account status/passwords and business progress are preserved. The root reset command clears application data in the eight exact local development DBs and project queue contents, retains schema/migration records, then reinstalls the fixed RBAC catalog.

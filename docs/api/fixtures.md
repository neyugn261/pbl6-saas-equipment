# Development fixtures (fixed ids)

Dev seeds of different services refer to each other only by these ids, so
each service can seed its own database independently and the data still fits
together. Add a row here in the same PR that adds the seed.

| Entity | Id | Code / name | Seeded by | Used by |
|---|---|---|---|---|
| Tenant DEMO | `00000000-0000-4000-8000-000000000001` | `DEMO` | identity (`tenant_directory`, now); organization (`tenants`, M1) | every service |
| Customer DEMO-CUST-01 | `00000000-0000-4000-8000-000000000101` | `DEMO-CUST-01` | organization (M1) | identity (`user_customer_links`), asset, service-request |
| Membership of `customer.admin@demo.local` | `00000000-0000-4000-8000-000000000201` | — | organization (M1); identity link already seeded | identity |
| Membership of `customer.user@demo.local` | `00000000-0000-4000-8000-000000000202` | — | organization (M1); identity link already seeded | identity |

Reserved ranges (last 12 hex digits) for the next seeds:

| Range | Entities | Owner |
|---|---|---|
| `…0000000001xx` | customers | organization |
| `…0000000002xx` | customer memberships | organization |
| `…0000000003xx` | branches | organization |
| `…0000000004xx` | customer sites | organization |
| `…0000000005xx` | locations | organization |
| `…0000000010xx` | equipment models | asset |
| `…0000000011xx` | equipment | asset |
| `…0000000012xx` | warranties | asset |
| `…0000000020xx` | service requests | service-request |

User ids are generated by Identity's seed; services that need them look them
up by email at seed time (or read them from a token in tests).

# ADR 0007 — Maintenance ownership, snapshots and recurrence

- Status: **Accepted**
- Decision date: 2026-10-23 (team review, D12a–e)
- Scope: M2 Maintenance implementation
- References: [ADR 0002](0002-workorder-maintenance-task-index.md), [ADR 0003](0003-customer-scope.md), [ADR 0004](0004-service-auth-and-authorization.md), [ADR 0005](0005-event-transport.md), [ADR 0008](0008-m1-review-decisions.md), [Maintenance API](../api/maintenance.yaml)

## Context and ownership

`maintenance_db` owns `maintenance_plans`, `maintenance_tasks`, its outbox and
inbox. Asset owns Equipment; Work Order owns Work Orders. IDs across these
databases are logical references, never cross-database foreign keys or joins.
The current Maintenance schema has no customer/site snapshot on plans, while
`MaintenanceTaskDue.v1` already requires `customerId` and permits a null
`customerSiteId`. The scheduler has no user token and must not fabricate one to
call Asset.

## Decisions

### D12a — A plan follows its Equipment

On creation, Maintenance validates an Equipment reference through Asset with
the caller's token and correlation ID. It stores `customer_id UUID NOT NULL`
and `customer_site_id UUID NULL` on the plan from the scoped Asset response.
The caller cannot supply these snapshot IDs. CUSTOMER_ADMIN may read only the
plans and tasks of its token customer; CUSTOMER_USER has no
`maintenance:read` permission in the current catalog.

When Equipment moves, the plan follows it. Asset will publish a versioned
`EquipmentMoved` event; Maintenance will update the plan's customer/site
snapshot idempotently and reject stale or out-of-order moves. The event
contract and the way to order moves must be reviewed before either producer or
consumer is implemented. A scheduler must not publish a task with a snapshot
known to be stale. No service reads `asset_db` directly.

### D12b — RETIRED and PAUSED plans

New plans cannot be created for RETIRED Equipment. A PAUSED plan produces no
tasks. On resumption, scheduling continues from the day it is resumed and does
not create tasks for periods missed while paused. INACTIVE plans produce no
tasks. The transitions involving INACTIVE and edits to a plan after tasks exist
were not decided in D12; those API operations require a separate review before
implementation.

### D12c — Calendar dates

Scheduling uses calendar dates in `Asia/Ho_Chi_Minh`. When a target month
lacks the plan's day (for example, the 31st), use that month's last day. The
M2 implementation must specify and test the recurring anchor, leap-day
behavior and interaction with completion time before coding the scheduler;
the team review did not settle those finer rules.

### D12d — Scheduler downtime

After downtime, the scheduler creates at most one catch-up task for each due
plan: the most recent missed occurrence. It skips older missed occurrences and
advances the plan to its next future due date. PAUSED and INACTIVE plans remain
excluded. The unique key `(maintenance_plan_id, scheduled_date)` and a
transaction containing the task, outbox event and date advancement prevent
duplicate tasks when ticks repeat or instances run concurrently.

### D12e — Cancelled Work Order

When a Work Order is cancelled, its Maintenance Task waits for a replacement
Work Order; it returns to PENDING. The replacement keeps the same task ID and
scheduled date. Work Order's partial unique index allows a new non-cancelled
Work Order after a cancellation (ADR 0002). Consumers correlate
`WorkOrderCreated`, `WorkOrderCompleted` and `WorkOrderCancelled` by
`maintenanceTaskId`, process events idempotently through the inbox, and must
not let an older cancellation overwrite a newer replacement or a completed
task. Retry limits and backoff remain operational details for the M2 consumer
design; no unlimited automatic retry is implied by this decision.

`MaintenanceTaskDue.v1` does **not** need `createdBy`. It is generated by the
scheduler, not a user action. A Work Order created from that event has
`work_orders.created_by = NULL` and retains the source task ID and event
correlation ID (ADR 0008 D5). The `tenantId` comes from the event envelope;
the task payload carries the customer/site snapshot required by Work Order.

## Implementation consequences

- Add the plan snapshot columns through a **new** Maintenance migration and
  update the ERD and Prisma schema in the implementation PR. Never edit
  `0001_init`. Before migration, count existing plans. If any exist, backfill
  through a reviewed authenticated Asset integration; do not invent IDs or
  query Asset's database.
- Add and review the `EquipmentMoved` contract and Asset producer before the
  Maintenance consumer and scheduler rely on it. Define ordering and replay
  behavior in that contract; use the Maintenance inbox for idempotency.
- The Plan API forwards the caller token and correlation ID to Asset. Tests
  use a fake plus a real integration path when Asset is available. No fake
  runs in production.
- Scheduler and consumers use Maintenance's database transactions, outbox and
  inbox. Outbox delivery does not make two service databases one transaction.
- M2 tests cover month end, leap year, pause/resume, downtime, concurrent
  ticks, transaction rollback, equipment moves, cancelled Work Order
  replacement and customer isolation on a database whose name contains
  `test`. Maintenance needs its own test DB/env and CI command. Gateway routes
  and frontend screens belong to their respective owners.

This ADR records the agreed M2 behavior and prerequisites. It does not add the
event contract, migration, scheduler, Plan API or consumer implementation.
